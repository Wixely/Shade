## Implementation decision

The Linux UI launches an owned X11 worker from the same executable. Xlib has process-wide error handlers, so native failures are isolated from CupriFace and its rendering libraries. Redirected standard input/output carry application state records; no listener, daemon, integration installation or external service is added. The supervisor reconnects after failures with bounded backoff, removes stale connected displays, times out unresponsive commands and terminates only its own worker. Closing the parent pipe makes the worker close every owned overlay and flush settings.

The worker blocks in XNextEvent when idle. Static black override-redirect windows use compositor opacity, empty input shapes and an input-disabled WM hint. XRandR notifications reconcile geometry and monitor presence. Retry timers run after failures, and settings writes debounce for 750 ms. Global changes batch selected levels in one request. The shared settings, assignment and control-intent model is used on both platforms.

Trustworthy EDID identities do not depend on geometry or connector. Fallback assignment connections use XRandR output names, not transient X resource IDs. Explicit assignments still identify connections rather than indistinguishable physical hardware. The native event ABI currently targets Linux x64. Missing compositor, recovery key or required extensions prevents active shading.

## Evidence and limits

A self-contained Linux x64 test publish ran in WSL without installing a .NET runtime. XRandR 1.6 reported six surfaces, compositor ownership and no trusted EDID identities. Native bounds and empty input shapes were read back for created undimmed windows. The worker recovered after forced termination and exited on backend disposal. An undimmed two-second sample recorded 0 ms worker CPU and zero state publications; this is not gaming or active-overlay performance evidence.

Active-overlay acceptance failed: the WSLg/Xwayland compositor gave keyboard focus to a mapped 3% overlay despite its non-interactive hints. An additional notification-type hint did not resolve this and was removed. Shade now listens for overlay focus events, hides all overlays on this condition, reports the incompatibility and prevents remapping for the remainder of that worker session. The dedicated WSLg focus-guard test passed, including attempted re-enable and topology refresh. This verifies failure handling, not successful WSLg shading. The active-overlay acceptance test remains deliberately separate and must pass on supported desktops.

No physical X11 desktop, native Wayland shading, mapped opacity readback, real pointer routing, keyboard recovery gesture, live Linux CupriFace host, desktop credential store, or Linux Home Assistant setup acceptance has passed yet. An ephemeral published-app launch reported EGL/Mesa device initialization errors; a software launch reported selecting SDL. Both bounded launches ended and left no owned Shade process, but these logs do not establish correct rendering or interaction. WSLg does not establish coverage of native Wayland surfaces or the Windows desktop. Current lock-modifier handling also needs validation beyond the conventional NumLock/Alt mapping.

## Sources and next actions

### X11 recovery modifier mapping, 2026-09-10

The worker no longer assumes Alt is Mod1 or Num Lock is Mod2. It reads `XGetModifierMapping`, resolves Alt and lock keycodes, and registers the required Shift/Control/Alt combinations with each actual Caps/Num/Scroll lock state. Zero keycodes are ignored; an absent or ambiguous mapping does not invent a shortcut. Allocation ownership, modifier ordering and mapping events follow the official [Xlib keyboard specification](https://www.x.org/releases/X11R7.6/doc/libX11/specs/libX11/libX11.html).

Core keyboard/modifier `MappingNotify` events refresh Xlib's keyboard cache and replace recovery grabs automatically. Existing grabs remain until all replacements succeed. Failed registration releases partial grabs, hides overlays and enables a one-second failure-only retry. Successful registration stops that timer. Paused settings remain available for restoration when the shortcut becomes available again.

Shared tests pass for Alt on two modifier slots, Num Lock moving between slots, Caps/Scroll combinations, zero keycodes and conflicting Alt/lock bits. The self-contained Linux worker passes native startup, focus-guard, crash/reconnect and disposal checks with the new mapping logic. An isolated `--linux-hotkey` check uses an owned helper to hold only Ctrl+Alt+Shift+F11, verifies that the worker disables shading during contention, releases the helper and verifies automatic registration recovery without manual refresh. It changes no system keyboard mapping. After recovery, the existing undimmed idle check recorded zero publications and 0 ms worker CPU in one two-second sample; this is not gaming acceptance.

Physical key delivery under real keyboard-layout changes, additional XKB arrangements and active shading on a representative X11 desktop remain unverified. The available WSLg focus incompatibility is unchanged; these hotkey improvements do not constitute Linux desktop acceptance. Repeat with the published test executable using `--linux-hotkey --linux-worker --linux-focus-guard`.

The available WSL session exposes a Wayland socket, but no `wayland-info`, `weston-info` or `wayland-scanner` executable was found. An original read-only .NET probe now connects to the session's Unix socket, creates a registry, waits for a sync callback and reports advertised interface names, versions and counts. It creates no surfaces and binds no input/output globals. The request layout, native-endian wire words and string alignment follow the official [Wayland wire format](https://wayland.freedesktop.org/docs/book/Protocol.html) and [core protocol specification](https://wayland.freedesktop.org/docs/html/apa.html). No library, utility, compositor or protocol package was installed.

The self-contained Linux test executable passed `--wayland-probe` against the live WSLg compositor. The probe is test-only, has a three-second deadline and bounded event/name parsing, and closes its socket on completion or failure. ### Native Wayland output catalog, 2026-09-10

Original `WaylandWire` and `WaylandOutputCatalog` now provide a long-lived, event-driven logical display catalog. Geometry comes from xdg-output, preserving fractional-scale and rotated logical dimensions separately from pixel modes. Pending properties become visible only at the protocol's completion event: xdg-output done for version 2, core output done for version 3. Registry additions bind new outputs automatically; removal retires them and releases supported protocol objects. Manager loss reports failure for a future worker supervisor. Published snapshots are immutable and cached; 1,000 repeated unchanged reads allocated zero bytes in both Windows and Linux checks.

The live `--wayland-catalog` check passed against all six WSLg outputs, with positive logical bounds, unique connection IDs, no claimed hardware identities and zero catalog revisions during a two-second observation. An owned loopback protocol peer additionally passed initialization, partial-batch isolation, rotation, add/remove, stale-event rejection, replug under a different registry number, cross-session connection identity and manager disappearance for xdg-output versions 2 and 3. These are simulated topology changes, not physical hotplug acceptance. The full default checks passed on Windows and the self-contained Linux test executable after these additions.

Names are hashed as explicitly untrusted connection identities. They are independent of geometry and registry numbering, but cannot prove physical monitor identity. Missing or duplicate names receive session-only IDs. Source: the official project's [xdg-output protocol XML](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/unstable/xdg-output/xdg-output-unstable-v1.xml), reviewed 2026-09-10, and the core/wire references above. No protocol implementation or generated bindings were imported.

At this catalog milestone, the application backend did not yet select Wayland; see the worker integration below. Cancellation during a read ends use of that connection. No native Wayland shading acceptance is claimed.

### Wayland surface and buffer implementation, 2026-09-10

`WaylandOverlaySession` now connects the native catalog to an original layer-shell surface lifecycle. It requires compositor v4, layer-shell v1, viewporter v1 and SHM v1, checking these before allocating a pool or creating surfaces. Each enabled output receives an explicitly targeted overlay-layer surface, all-edge anchors, no exclusive space reservation, an empty input region and keyboard interactivity set to none. A bufferless initial commit waits for and acknowledges configure before mapping. Configure dimensions resize the viewport; unchanged levels send no surface requests. Disabling destroys the surface; re-enabling starts a fresh configure sequence. A compositor close removes all owned surfaces and reports failure to the future supervisor. Disconnect destroys the session's native resources.

The original Linux 64-bit `sendmsg` interop sends the SHM descriptor using SCM_RIGHTS, suppresses SIGPIPE, handles interrupted/backpressured sends and sends any remaining bytes without repeating descriptor transfer. No incoming descriptor-bearing protocol objects are bound. The palette contains 80 immutable one-pixel premultiplied black values in 320 bytes of pixel data, with levels using the shared `DimLevel.Alpha` conversion. Buffers are allocated lazily and shared unchanged across surfaces; viewporter performs scaling. This pixel-data size is not a measurement of total kernel/compositor/GPU memory or game performance.

Live `--wayland-buffers` passed: WSLg accepted all 80 buffers and their destruction across sync barriers. An initial write-sealed pool failed because libwayland-server maps pools read/write; the corrected pool seals size and further seal changes, and Shade closes its descriptor without subsequent pixel writes. `--wayland-no-layer` passed the explicit WSLg startup limitation check without mapping surfaces. Owned protocol-peer tests passed on Windows and Linux for configure-before-map ordering, explicit output/layer selection, empty input region, no keyboard focus requests, resizing, unchanged-level silence, full-batch validation, disable/re-enable, stale configure rejection and compositor-close cleanup. These verify requests, not visible compositor behavior or real input routing.

Sources reviewed 2026-09-10: [layer-shell protocol](https://raw.githubusercontent.com/swaywm/wlr-protocols/master/unstable/wlr-layer-shell-unstable-v1.xml), [viewporter protocol](https://raw.githubusercontent.com/wayland-mirror/wayland-protocols/main/stable/viewporter/viewporter.xml), core protocol above, [sendmsg](https://man7.org/linux/man-pages/man2/sendmsg.2.html), [ancillary messages](https://man7.org/linux/man-pages/man3/cmsg.3.html), [memfd_create](https://man7.org/linux/man-pages/man2/memfd_create.2.html), and [libwayland SHM mapping behavior](https://raw.githubusercontent.com/wayland-mirror/wayland/main/src/wayland-shm.c). Protocol declarations informed original code; no generated bindings or external implementation were imported.

At this surface milestone, worker/settings integration remained outstanding; see the integration below. Actual layer-shell shading, stacking, input routing, desktop credentials and the full Linux UI remain unverified.

### Native Wayland recovery client, 2026-09-10

`WaylandRecovery` implements the Global Shortcuts portal using the existing pinned Tmds.DBus.Protocol 0.94.2 dependency, now explicitly referenced by Shade. A dedicated bus connection owns the session. The client checks portal availability, pins the unique portal owner, subscribes before sending requests, validates request/session paths, requests `restore-all` with preferred `CTRL+ALT+SHIFT+r`, and requires a returned binding with a trigger description before becoming ready. Activation is restricted to the owner, session and shortcut. Binding removal, session close, reader failure, owner change and connection loss revoke readiness. Setup cancellation disposes the connection, including a stalled portal request.

The overlay session now rejects positive levels without confirmed portal recovery. Loss of recovery disconnects that Wayland session, removing its native surfaces even if the future worker is waiting for another event. This guard is implemented, but its visible-surface effect still requires a compatible compositor test. Portal readiness does not prove real physical shortcut delivery.

`--wayland-recovery` passed in the self-contained Linux test executable against an owned isolated `dbus-daemon` and original fake portal. It tests response-before-method-reply ordering, successful binding, sender/session/action filtering, denied and empty bindings, stalled-request cancellation, shortcut removal, session close and portal owner loss. No existing desktop portal, shortcut configuration or service installation was changed. The available user bus had no running portal owner during the read-only capability check; no real authorization dialog or keyboard gesture was tested.

Source: [Global Shortcuts portal specification](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.GlobalShortcuts.html), reviewed 2026-09-10. Library API signatures were checked against the exact restored package's XML documentation; no bindings generator was introduced. The returned trigger description must be shown in the UI because the desktop/user may choose a different chord. Worker integration must distinguish a denied setup from a dropped connection and avoid repeatedly opening authorization dialogs during automatic retries.

### Worker and UI integration, 2026-09-10

The application now selects `WaylandOverlayWorker` when a Wayland session/display is advertised; otherwise it uses X11. Isolated X11 test-key runs continue selecting X11 explicitly. The existing supervised child-process pipe carries both workers' snapshots and commands. Wayland handles effective-level batches, global/control preferences, explicit connection assignments, settings recovery, restore-all (including detached enabled intent), debounced saves and automatic compositor reconnect with 1–30 second backoff. Native reading is separated from dispatch so only the worker actor changes state or writes protocol requests. Surface writes have a two-second deadline and disconnect on timeout; ordinary native reads block without a recurring timer.

Compatible sessions initially remain undimmed and expose **Set up recovery shortcut**. Only that UI action opens portal authorization; failure or denial leaves a retry action instead of repeated dialogs. Successful registration reconnects the overlay session with recovery enabled and reconciles saved assigned-screen controls. Trigger-description changes update the status. Losing recovery closes the native session; automatic reconnection remains undimmed until the user establishes recovery again. Unassigned Wayland connection identities never become hardware-trusted automatically.

### Session identity and long-running object reuse, 2026-09-10

Linux single-instance identity and backend selection now share `LinuxDesktopSession`. Wayland locks use the normalized native socket endpoint and user identity, independently of the optional Xwayland `DISPLAY`. Relative socket names and equivalent absolute paths produce the same lock; different sockets/runtime directories/users remain distinct. X11 sessions continue using their display endpoint. An inherited `WAYLAND_SOCKET` selects the native path and its explicit unsupported-descriptor status, instead of silently choosing X11. Unit checks cover these identity relationships on Windows and Linux; actual multi-session desktop lock contention remains unverified.

Wayland object IDs are now reused only after `wl_display.delete_id` acknowledgment. Allocation and acknowledgment processing share a lock because the background reader and worker actor can run concurrently. Unknown/duplicate acknowledgments are rejected. Tests verify no reuse before acknowledgment, 100 repeated reuse cycles without increasing IDs, and duplicate rejection. The complete worker fixture now emits deletion acknowledgments and still passes hotplug/reconnect/restore tests. Live WSLg SHM buffer creation/destruction also passes with reuse enabled. This bounds object-ID growth over repeated screen toggles; it is not a measurement of compositor or gaming cost.

Visible-test environment check: no `sway`, `labwc`, `kwin_wayland`, `weston`, `gnome-shell`, `Xvfb` or `Xephyr` executable was found on the available Linux PATH. No compositor or test server was installed. WSLg remains useful for catalog/buffer checks but lacks layer-shell.
