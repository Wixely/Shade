# Release automation

Reviewed 2026-11-09. Owner: Codex. Review when changing dependencies or release behavior.

Push an annotated `v<Version>` tag. The Release workflow checks out the exact tagged commit, installs the SDK from `global.json`, derives `<Version>` from the tag itself (stripping the leading `v`), verifies vendored sources, restores locked dependencies, runs shared/MQTT tests, and packages Windows x64 — all with `-p:Version=<Version>` passed through to `dotnet run`/`dotnet publish`, so the tag is the single source of truth for both the running tests and the shipped executable's embedded version metadata. Nothing in `src/Shade/Shade.csproj` needs to change between releases; the `<Version>` left there is only a placeholder for ad-hoc local builds run without a tag. It publishes a ZIP and SHA-256 checksum through GitHub Releases. Versions containing a hyphen are published as prereleases and are never marked latest; versions without one are published as stable releases and become the repository's latest release. Existing tags and releases are never overwritten.

Release notes are generated by `gh release create --generate-notes` from the commits since the previous tag, matching Bantz and CursorGoblin's release process, rather than hand-authored per version. A per-version `docs/release-<Version>.md` with known-limitations disclosure was required through 1.2.2; that requirement was dropped on 2026-11-08 in favor of the auto-generated notes. The historical `docs/release-*.md` files remain as a record, and `docs/release-1.2.0.md#known-limitations` is still linked from the README as the last written limitations disclosure — update or replace that link by hand if those limitations change, since nothing generates it automatically anymore.

## Version handling

`src/Shade/Shade.csproj`'s `<Version>` is never read by the release pipeline — `release.yml` computes the real version from `GITHUB_REF_NAME` and passes it through `-p:Version=` to every build/test/publish step, and `scripts/package-release.ps1` / `scripts/prepare-release.ps1` accept it as a `-Version` parameter (falling back to the csproj value only when run locally without one, e.g. for an ad-hoc test build). The About-dialog test in `tests/Shade.Tests/Program.cs` reads `ShadeApp`'s own `AppVersion` property — which is populated from `AssemblyInformationalVersionAttribute`, itself generated by the SDK from whichever `Version` was in effect at build time — and only checks that it looks like a version string, not an exact literal. So pushing a release tag never requires touching any file in the repo: there is nothing left to keep in sync by hand.

The workflow uses Windows PowerShell 5.1, Git, the .NET SDK and GitHub CLI. It does not use Node/Python actions, caches or workflow-artifact uploads; durable files live in Releases. The job has a 30-minute timeout, serializes runs per tag, and grants only `contents: write`. The GitHub token is passed only to the release step. A release stays a draft until both uploads succeed. If a run fails after creating a draft, inspect that draft before rerunning; automatic overwrite is intentionally disabled.

The SDK installer is pinned to the official dotnet/install-scripts commit `47940ac9fc30a2f2dd19167165d0bb0774625f67`. Microsoft documents this PowerShell installer for [CI SDK installation](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-install-script). Release creation uses the documented [GitHub CLI](https://cli.github.com/manual/gh_release_create) draft, prerelease, generate-notes and verify-tag options.

## Windows archives

Each release publishes two Windows archives from the same source and the same gates:
`Shade-<Version>-win-x64.zip`, the untrimmed self-contained single file every release has shipped, and
`Shade-<Version>-win-x64-aot.zip`, compiled ahead of time with NativeAOT. The untrimmed one stays the
recommended download; the ahead-of-time one is offered beside it, not in place of it, so a machine it
misbehaves on still has a build that runs.

`prepare-release.ps1 -Aot` produces the second. NativeAOT compiles and trims in one step, so
`PublishTrimmed` and `PublishSingleFile` take no part; the project's `EmbedNativeDependencies` target
embeds the unmanaged dependencies instead, and `package-release.ps1` refuses an ahead-of-time
candidate containing more than one executable, which is what proves the embedding happened rather than
the libraries being silently dropped. `TreatWarningsAsErrors` is relaxed for that publish alone,
because Silk.NET's native-asset resolver raises `IL3000`/`IL3002` against APIs that return nothing in
a single-file application; the warnings are deliberately left visible in the log rather than
suppressed. NativeAOT needs the MSVC linker, which the `windows-2025` runner provides.

Ahead-of-time compilation cannot cross-compile between operating systems, so a Linux ahead-of-time
build would have to be produced on Linux, and the embedded-library restore is Windows-only.

Locally, run `./scripts/package-release.ps1` in a workspace with fresh output directories. It verifies executable version metadata, collects dependency/runtime notices, excludes debug symbols and unexpected file types, and generates the archive checksum. Release archives contain only the executable, license notices and checksums. No screenshots, settings or test logs are included. A successful pipeline does not establish physical display, gaming or Linux desktop acceptance; see `docs/release-1.2.0.md#known-limitations` for the last written statement of these limits.

Before pushing a release tag, review all outgoing commits and assets for privacy. Build-generated binary output must contain no user settings, credentials, PDB files or local diagnostic output. License attribution is preserved intentionally. Never move a published tag to retry a release; fix forward with a new version when source changes are required.
